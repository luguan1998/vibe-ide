  InputHandler（InputHandler.ts:539）发现——字符列宽的真决口是

  InputHandler.print()
    └→ unicodeService.charProperties(code, precedingJoinState)  ←

         └→ GraphemeProvider.charProperties()                      ← 决定列宽

  getStringCellWidth 只在 TextureAtlas
  渲染字形时调用一次，改它治不了写入时的列宽！

  真凶在此（GraphemeProvider.charProperties:35）：

  if (w >= 2) {   // ← 仅当 trie 数据标记 U+FE0F 为 WIDE 时才进入
      w = codepoint === 0xfe0f ? 2 : 1;  // 虽有特殊处理，但被外层的 if (w >= 2)
   禁锢
  } else {
      w = 1;  // trie 若标记 NORMAL，直接落此，FE0F 永远 1 列宽
  }

  若 trie 将 U+FE0F 标为 NORMAL(0)，则 w=1，keycap 序列四舍五入只得 1 列。

  🎯 正确施术点

  不该劫 getStringCellWidth，应劫 GraphemeProvider.charProperties——在 FE0F
  时强制 w=2：

  // 在 UnicodeGraphemesAddon 加载后
  const provider = (term as any)._core._unicodeService._activeProvider
  const orig = provider.charProperties.bind(provider)
  provider.charProperties = function(code: number, pre: number): number {
    const r = orig(code, pre)
    // U+FE0F (variation selector-16): 终端下表情应占 2 列
    if (code === 0xFE0F && ((r >> 1) & 3) < 2) {
      return (r & ~6) | 4  // 清 width bits → 置为 2，保留 shouldJoin/kind
    }
    return r
  }

  ---
  🎯 一句话版

  4️⃣ 这个表情，Claude Code 觉得它占 2 个格子宽，但我们的终端只给它 1 
  个格子宽。差了 1 格，整行排版就歪了，后面的空格看起来像丢了。

  ---
  🔍 为什么会算错？

  4️⃣ 不是单个字符，是三个字符叠出来的：

    '4'   +   ︎   +   ⃣
  (U+0034)  (U+FE0F)  (U+20E3)
   数字4    变体符     封闭按键帽
   1列宽    0列宽      0列宽

  xterm.js 里面有个"字典"（trie），专门查每个字符该占几列。它查
  U+FE0F（变体符），老老实实返回 0——因为变体符本身确实不占宽度。

  然后代码把三个字符的宽度一加：1 + 0 + 0 = 1 列。错了，正确应该是 2 列。

  作者其实留了一段补救代码——"遇到 FE0F 就强制给 2 列"。但这代码被一层 if 条件
  锁在里面，永远执行不到。前人修了一半，锁没开。

  ---
  💉 我们的补丁干什么

  就在 charProperties 这个函数上打个补丁：

  ▎ 只要看到码点 = 0xFE0F，不管字典怎么说，直接给 2 列宽。

  3 行代码，只在一个码点上拦截。类似于：

  原本: 查字典(fe0f) → 0列 → 被 else 吞了 → 变1列 → keycap 算成1列
  修复: 查字典(fe0f) → 0列 → 被我们拦截！→ 强改2列 → keycap 算成2列 ✓

  ---
  ⚡ 性能有没有影响？

  没有。

  charProperties 是每个字符写进终端时必调的函数，我们的补丁只加了三样东西：

  ┌─────────────────┬─────────────────┬────────────────┐
  │      操作       │      耗时       │      频率      │
  ├─────────────────┼─────────────────┼────────────────┤
  │ code === 0xFE0F │ 一次整数比较    │ 每字符 1 次    │
  ├─────────────────┼─────────────────┼────────────────┤
  │ (r >> 1) & 3    │ 一次位移+按位与 │ 仅 FE0F 命中时 │
  ├─────────────────┼─────────────────┼────────────────┤
  │ (r & ~6) | 4    │ 一次按位或      │ 仅 FE0F 命中时 │
  └─────────────────┴─────────────────┴────────────────┘

  终端每秒处理成千上万个字符，其中 99.99% 不是 0xFE0F（Claude Code
  一次输出可能就一两个表情）。99.99% 的情况只走一次整数比较，比 if (x > 5)
  还便宜，完全无感。

  Claude Code 跑满屏时 TUI 每帧可能写几百个字符——几百次整数比较 =
  纳秒级，不值一提。
